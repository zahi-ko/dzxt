# ADR 0001：音频采集与播放由后端独占

- **状态**：已接受
- **日期**：2026-09-02
- **相关**：PLAN.md 阶段二 2.1 / 2.4

## 背景

系统需要采集麦克风输入并播放处理结果。Web 架构下有两个选择：浏览器采集（MediaRecorder / Web Audio API）或后端采集（sounddevice / PortAudio）。

## 决策

**采集与播放全部在 Python 后端完成。** 前端只下发指令、展示波形与频谱，不接触音频设备，也不持有音频数据。

## 理由

1. **采样率与格式统一。** 浏览器录音输出的是 WebM/Opus，采样率由浏览器自行决定，传到后端还要解码与重采样。后端采集可以直接锁定 16k/44.1k/48k 与 float32，整条处理链路零格式转换。
2. **前端彻底退化为展示层。** 契合「API 优先、避免调试 GUI」的整体策略，音频逻辑全部集中在可测试的 Python 侧。
3. **接口负载恒定。** 音频不以 base64 在 HTTP 上往返，而是留在后端由 `audio_id` 引用。
4. **实时性更好。** 录音电平通过 WebSocket 推送几十字节的标量，比在浏览器里做音频分析再上传轻量得多。

## 备选方案

| 方案 | 优点 | 未选原因 |
|---|---|---|
| 浏览器采集 + 上传 | 可跨网络部署，不依赖服务器声卡 | 格式不可控、需重采样、大负载传输 |
| 双后端（浏览器 + 后端可切换） | 部署灵活 | 抽象层与联调成本高，本项目用不上 |

## 后果

- **限制**：只能在后端所在机器上使用，不支持远程部署。课程项目现场演示在本机运行，此限制无影响。
- **补偿**：保留文件上传与下载接口，作为无麦克风环境的兜底通道。
- 若未来需要远程部署，在 `server/core/io/` 增加 `RemoteAudioBackend` 实现同一接口即可，上层无需改动。
