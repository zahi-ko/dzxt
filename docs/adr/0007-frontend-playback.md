# ADR 0007：播放改由前端承担

- 日期：2026-09-07
- 状态：已接受
- 关联：ADR 0001（音频 I/O 放后端）

## 背景

阶段二 2.4 要求「播放/暂停/停止、进度拖动与实时播放指针、变速播放」。
原实现按 ADR 0001 把播放放在后端（`sounddevice.play`），它有两个硬伤：

1. `sd.play` 是「发射后不管」，PortAudio 没有暴露播放位置查询接口，
   进度条与实时指针无从实现；
2. 没有 pause/resume 语义，只有 `sd.stop()`，无法「暂停后接着播」；
3. 播放速率只能在打开输出流时指定，中途变速要重建流，会咔哒一声。

## 决策

- 新增 `GET /api/audio/{id}/stream`，以 `Content-Disposition: inline` 返回 WAV；
- 前端用 `HTMLAudioElement` 播放，进度、暂停、变速全部由浏览器承担；
- 后端 `/api/audio/{id}/play`（本机扬声器播放）保留，作为浏览器音频不可用时的退路。

## 对既有契约的影响

铁律二「前端唯一接触音频二进制的场景是导出下载」需要放宽为：
**导出下载与播放流**。两者的共同点是——都是终点消费，音频不再回到处理链路；
链路内部依旧只传 `audio_id`，波形本体始终不离开后端。

## 代价

- 多一次音频传输（WAV 未压缩）。本地/局域网场景可忽略；
- 打包分发时前端与后端同源，`/api/...` 相对路径仍然成立，无需额外配置。

## 备选方案（未采纳）

- **后端维护播放状态机 + 轮询位置**：需要自己记录开始时间与播放速率去估算
  播放位置，误差累积且要处理缓冲，得不偿失。
- **Web Audio API 接二进制流**：能做可视化，但进度与变速要自己实现一遍，
  `<audio>` 元素已经免费给了。
